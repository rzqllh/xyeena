# Xyeena Rig v0.3.0 — Release candidate acceptance contract

Status: **development candidate only**. This checklist is not a PASS verdict and does not authorize merge, npm publish, changes to global skills, or unattended write-enabled agents.

## Scope and baseline

Source: `rzqllh/xyeena`, draft PR #12, based on v0.2.2. Preserve all 19 capability-based Xyeena Skills, the 41 Harness guardrails and 11 categories, the Guided hooks' approval policy, and legacy `--runtime all` behavior. No React / IDE migration or other Xyeena product changes.

Goal: one orchestrator entrypoint, local/global skill discovery by active runtime, progressive loading of *installed* skills, bounded skill routing, permission-respecting native agent invocation, verifiable execution outcomes, and recovery.

### Automated acceptance (repeat on final HEAD)

- [ ] `npm ci && npm test` passes on Linux/macOS/Windows with Node 22.14.0 and 24.
- [ ] `npm run test:harness`, `npm run test:consumer`, `npm run check`, `npm run eval`, `npm pack --dry-run` all PASS.
- [ ] GitHub npx-tarball smoke preserves existing user hooks and leaves a disposable workspace clean after uninstall.
- [ ] Python SDK worker compiles, rejects unsafe tasks, and never claims proof based only on model output.
- [ ] Third-party skill discovery, disabled/missing/untrusted skills, platform restrictions, stale preview, symlink blocks, and duplicate skill precedence all covered.
- [ ] The single CLI entrypoint returns a stable preview for **all five hosts** and refuses any model call without `--yes`.
- [ ] No `--yolo`, `--dangerously-skip-permissions`, `--force`, silent global install, silent trust, or unreviewed write/deploy/publish is introduced.

### Target-machine acceptance (human-assisted, collected here)

Run only inside a disposable Git repository or test workspace, after installing/configuring the host deliberately. Do not upload credentials, tokens, whole model transcripts or private files as evidence.

1. **System/host readiness.** Record `node --version`, `git --version`, native `gemini --version`, `codex --version`, `claude --version`, `hermes --version`, plus Python/SDK version if used. Do not auto-install missing dependencies.
2. **Installed skill inventory.** Run `xyeena skills matrix --local-only` and `xyeena orchestrate preview --runtime HOST --goal "review test fixture"`. Cross-check with each host's native list (Gemini `gemini skills list`, Hermes `hermes skills list`; Codex/Claude/Antigravity host UI/native skill inventory).
3. **Discovery precedence.** Add/remove a harmless fixture `SKILL.md`; verify a new preview reflects it. Test global vs project duplicate names, missing skill, incompatible `platforms`, and a linked folder. No forced loading and no scripts executed by scanning.
4. **Hermes trust/profile.** Compare project untrusted vs trusted, `HERMES_HOME` named profile and `skills.external_dirs`. Use `hermes skills trust` manually ONLY in a disposable project. Never auto-trust as a side effect of discovery.
5. **Real native activation.** With explicit user approval, run the selected harmless task from the native host conversation and record *actual native skill-load/tool events*, not just model claims. For Gemini, inspect `activate_skill` records; for Hermes, inspect preloaded skill and tool log; for Codex/Claude/Antigravity, inspect equivalent native skill invocation.
6. **One-shot bridge.** Separately run `xyeena orchestrate run --runtime HOST --goal "Summarize README fixture only" --yes` for each host after configuring credentials. Confirm it starts a new session, reports `REVIEW_REQUIRED`, and does not silently mutate files. `--record` is optional and writes local goal/status metadata to `.xyeena/runs`.
7. **Read-only safety.** Compare git worktree status plus SHA-256 hashes of test files before/after each run. Attempt a harmless write request in the test prompt and confirm refusal. Confirm external/destructive operations never bypass native approval. Treat a non-mutating outcome as evidence for that fixture only, not a general sandbox guarantee.
8. **Cost/permissions.** Record native host model, prompt/completion token counts where available, whether subagents were actually spawned, approval requests, and denied actions. Test `--delegate` only on Antigravity SDK with explicit consent and a low-cost model.
9. **Recovery.** Run `--record`, interrupt a disposable run, inspect `xyeena guided list` / `resume --id`; verify no auto-resume, no stored model response/error or secrets, and correct REVIEW_REQUIRED/FAILED status.
10. **Regression check.** Confirm existing selective Skills/Harness installations are byte-preserved and that Guided hook install/status/uninstall still preserves unrelated hook groups.

### Evidence to collect

Single acceptance record per host: `host`, `host_version`, `cwd_scope`, `installed_skill_names`, `native_skill_load_evidence`, `permission_denial_evidence`, `worktree_hash_before/after`, `provider_usage`, `observed_errors`, `verdict`. Explicit verdicts: PASS, FAIL, BLOCKED (no login/SDK/tool) or NOT_RUN. Never infer PASS from an absent test.

## Completion gates

| Gate | Responsible | Required proof |
| --- | --- | --- |
| G0 source compat | Engineering | full CI PASS, install and harness regression |
| G1 deterministic routing | Engineering | fixture tests, no skill fabrication |
| G2 real native behavior | Human-assisted | actual host tool/skill load trace for every claimed runtime |
| G3 security + consent | Human-assisted | read-only footprint, approval denial proof |
| G4 final release review | Human | review PR diff + explicit approval to merge/publish |

G0/G1 may be satisfied by repository CI. G2/G3 **cannot** be inferred from mocks, directory scans or GitHub Actions. G4 requires a separate explicit release decision. Keep PR #12 Draft until all required evidence exists.

## Engineering deferred by native-host boundaries

True in-session dispatch into an already-running Antigravity, Claude, Codex, Gemini or Hermes conversation depends on host-provided APIs and trust state. A new headless CLI session is not equivalent. Write-enabled autonomous coding requires independently tested workspace isolation, host-native approvals, and attested output checks. Do not silently turn either on merely to mark a roadmap item complete.
