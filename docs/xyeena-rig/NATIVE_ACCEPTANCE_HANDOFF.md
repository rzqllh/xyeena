### Safe Antigravity IDE negative test (only when the operator is ready)

The [official Antigravity hooks documentation](https://www.antigravity.google/docs/hooks) specifies a workspace `.agents/hooks.json` and, for standalone IDE, agent side panel **… > Customizations > Hooks**. The operator must check that `xyeena-rig-guided` is visible and enabled in the **IDE**, not only `agy` CLI.

1. Inspect the existing workspace-local managed hook with `node bin/xyeena.mjs guided status --dir .` from a **current source checkout**. Do not install/overwrite, edit host permissions, or reset the user's worktree merely for testing. If the workspace checkout is older, use a separate checked-out source worktree with `--dir` pointing to the real project.
2. If and only if its managed runner and *entire PreToolUse* are intact, deliberately arm the bounded local diagnostic with `node bin/xyeena.mjs guided probe deny-start --dir . --yes`. This is **not read-only**: it creates a private, ignored, expiring **5-minute** local probe file; it does not grant permissions, call AI or install hooks.
3. In a **fresh standalone Antigravity IDE agent session opened on that workspace**, request **only** a native `run_command` executing `git status --short` with no explicit `Cwd`. It is intentionally harmless even if the IDE ignores Xyeena's deny. Do not run a write/delete/permission escalation test. Record whether the **IDE host** itself reports `tool call denied by pre-tool hook: Xyeena: native deny diagnostic blocked read-only git status`; capture only redacted host output and IDE version. If the command succeeds or the hook fails to launch, #34 remains BLOCKED.
4. Run `node bin/xyeena.mjs guided probe status --dir .` to inspect the untrusted local receipt, then `node bin/xyeena.mjs guided probe clear --dir . --yes` to clear only the diagnostic. A receipt generated by manually invoking Node is **never** acceptance evidence.

No unverified IDE build is certified merely because vendor docs describe its hook support. The existing project hooks, unrelated Coucou/other hook groups, and the user's `.gitignore` must be preserved.

### Other host gates

For Codex/Claude/Gemini, do **not** install, log in or launch a billable agent automatically. Collect binary/version hints via read-only `node bin/xyeena.mjs ops preflight --dir .` first. Native host work can occur only where those hosts are installed and user-authorized; don't equate a shared `.agents` directory with a running agent.

For Hermes, use an isolated read-only bounded task and actual terminal cancellation only after explicit operator consent, and verify no false `completed` result. Source `taskkill /T /F` requests do not prove every detached child or remote provider request has stopped. Provider-side spending controls are separately managed.

## Supply-chain publication controls (source-only)

The updated `.github/workflows/publish.yml` removes legacy push/commit-message publication and long-lived npm token fallbacks. It accepts **only an explicitly published non-prerelease GitHub Release** matching the package version, rejects tags whose commit is not the **current main HEAD**, rejects an already-published exact version, and uses npm's official Trusted Publisher OIDC path with provenance on a GitHub-hosted runner. This is source configuration, not proof of a successful publication.

**Prerequisites that must be configured externally before any release authorization:**

1. In **GitHub Settings → Environments → npm-publish**, require the intended human reviewers; merely naming an environment in YAML does not enable human approval. Prevent self-approval where supported.
2. In **npm package Settings → Trusted publishing**, configure the exact repository `rzqllh/xyeena`, workflow `publish.yml`, and any matching environment name. Enable the intended publication method; restrict or revoke long-lived tokens only after trusted publishing is confirmed usable.
3. Protect release tags and prefer immutable GitHub Releases if supported. Explicitly approve the `0.5.0` package/version promotion, exact tag and source SHA first. Do not create a GitHub Release until all requested evidence gates are either independently accepted or clearly excluded from the publicly advertised support scope.
4. Validate the released tarball, provenance and fresh registry consumer install after publication. A clean source CI alone cannot attest npm registry contents.

No environment protection state or npm Trusted Publisher account settings were read or changed by this repository patch. Publication remains `RELEASE_NOT_AUTHORIZED`.
