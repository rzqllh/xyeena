# Writing — v1 Procedure Entry

**Activate when:** A text artifact must persuade, instruct, explain, onboard, report, document API usage or reduce generic AI-style copy.

**Do not activate for:** A code bug report requiring implementation, a current external fact without research, or invented brand claims without evidence.

## Execution route

1. Establish audience, channel, purpose, voice, reading context, facts provided and what action the reader should take.
2. Collect concrete source material, truthful metrics and domain nouns; mark unsupported claims UNKNOWN or remove them.
3. Choose structure by job: procedural runbook, status report, UX error, sales page or concise technical decision. Do not apply one template to all.
4. Edit line by line for semantic precision, active verbs, rhythm, UI constraints and information hierarchy; protect legally required wording and code invariants.
5. Check factual claims and mechanics with a source/owner; test UX actions with actual flow where relevant; avoid quoting invented benchmarks or human testimonials.

**Output contract:** Audience-fit artifact, changed claims and sources, UX states or runnable doc steps, proof/unknown list.

**Failure boundary:** Replacing all adjectives or banning gradients/expressive writing is not a writing-quality proof; user constraints outrank generic taste rules.

Use [references/procedure.md](references/procedure.md) for decision, recovery, and adversarial cases. Use host-native execution and independent evidence, not an invented worker, host, verifier, or upstream runtime. This entrypoint alone is not evidence of behavior/host parity.
